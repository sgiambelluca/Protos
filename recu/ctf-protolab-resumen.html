Cómo funciona el challenge

Objetivo:responder 5 preguntas que expone el servidor HTTP 192.168.123.200. Al terminar se habilita el acceso al servidor SSH The Vault, que es la meta final.

El ciclo, para cada pregunta

  1. Entrar al contenedor del lab tu máquina (una sola vez; desde ahí se llega a .200) 
    $ ssh -o IPQoS=none -p 2222 user_5@192.168.0.238
  2. Leer la consigna contenedor: GET al recurso de la pregunta, siempre con el header Tiki: Taka
    bash
    $ curl -i http://192.168.123.200/<recurso> -H "Tiki: Taka"
  3. Resolverla. Cada pregunta toca un protocolo distinto y algunas se resuelven fuera del contenedor: fijate el 📍 de cada paso.
  4. Mandar la respuesta contenedor: POST <recurso>/response con body JSON {"rta": "..."}
    bash
    $ curl -i -X POST http://192.168.123.200/<recurso>/response \
  -H "Tiki: Taka" -H "Content-Type: application/json" \
  -d '{"rta": "<respuesta>"}'

Handshake inicial

HTTP/start
Qué se pide:leer la bienvenida y confirmar que entendiste cómo se responde.

P1

Gateway de pampero hacia 1.1.1.1

Routing/juialepan
Pregunta: ¿cuál es el gateway de pampero para llegar a 1.1.1.1?
La respuesta depende de la tabla de ruteo de pampero, no de la máquina propia: hay que correr el comando en pampero.

Qué hay que hacer

  1. Entrar a pampero tu máquina
    bash
    $ ssh -o IPQoS=none usuario@pampero.itba.edu.ar
  2. Preguntarle al kernel qué ruta usaría para 1.1.1.1 pampero. El gateway es lo que aparece después de via.
    bash
    $ ip route get 1.1.1.1
1.1.1.1 via 10.16.1.254 dev enp1s0 src 10.16.1.100
  3. Responder contenedor
    bash
    $ curl -i -X POST http://192.168.123.200/juialepan/response \
  -H "Tiki: Taka" -H "Content-Type: application/json" \
  -d '{"rta": "10.16.1.254"}'
Respuesta10.16.1.254el via = next-hop

Conceptos

ip route get <ip> resuelve qué ruta usaría el kernel para ese destino: devuelve via (gateway/next-hop), dev (interfaz) y src (IP origen elegida).

Si no hay ruta más específica, matchea la default 0.0.0.0/0 y su via es la respuesta.

P2

SERIAL del SOA

DNS/ketylanuchi
Pregunta: el router que expone el HTTP también expone un DNS. ¿SERIAL de www.google.com según ese DNS?
"Según ese DNS" = consultarle a 192.168.123.200 (con @ en dig), no al resolver de siempre. Su google.com es de mentira.

Qué hay que hacer

  1. Pedir el SOA a ese servidor contenedor. El SERIAL es el primer número después de los dos nombres (ns. y admin.).
    bash
    $ dig @192.168.123.200 www.google.com SOA
www.google.com.  CNAME  google.com.
google.com.  IN SOA  ns.google.com. admin.google.com. 74757169 69 420 666 69
  2. Responder contenedor
    bash
    $ curl -i -X POST http://192.168.123.200/ketylanuchi/response \
  -H "Tiki: Taka" -H "Content-Type: application/json" \
  -d '{"rta": "74757169"}'
Respuesta74757169

Los 5 números del SOA

74757169SERIAL
69REFRESH
420RETRY
666EXPIRE
69MINIMUM

Conceptos

El registro SOA vive en el ápex (raíz) de la zona, no en cada nombre. Como www.google.com es un CNAME a google.com, el SOA aparece bajo google.com.

SERIAL = versión de la zona; el admin lo incrementa en cada cambio. Los esclavos lo comparan con el suyo y, si el del master es mayor, transfieren la zona.

Flag aa = authoritative answer (es dueño de la zona, no cacheado). recursion requested but not available = DNS autoritativo puro.

P3

Content negotiation

HTTP/urururulururecurso /turulu
Pregunta: ¿contenido EN ESPAÑOL del recurso /turulu?
No hay que traducir: el servidor ya tiene la versión en español, hay que pedírsela con un header.

Qué hay que hacer

  1. Pedir el recurso tal cual contenedor: viene en inglés (Content-Language: en) y trae la pista X-Sugerencia → header Accept-Language.
    bash
    $ curl -i http://192.168.123.200/turulu
  2. Pedirlo en español contenedor
    bash
    $ curl -i http://192.168.123.200/turulu -H "Accept-Language: es"
Content-Language: es
Hoy aprendimos a negociar contenido sobre HTTP
  3. Responder con el cuerpo contenedor
    bash
    $ curl -i -X POST http://192.168.123.200/urururuluru/response \
  -H "Tiki: Taka" -H "Content-Type: application/json" \
  -d '{"rta": "Hoy aprendimos a negociar contenido sobre HTTP"}'
RespuestaHoy aprendimos a negociar contenido sobre HTTP

Concepto

Negociación de contenido (RFC 9110 §12). El cliente manda Accept-Language (o Accept, Accept-Encoding…) y el servidor elige la representación; responde Content-Language indicando cuál mandó.

P4

Token por mail

SMTPbase64/papopepoparapapapapiparapopepo
Pregunta: pedir un mail secreto a POST /maketoken?email=.... El token que trae el mail es la respuesta.
El endpoint manda un mail real por SMTP ("no a cualquier dirección"): necesitás un buzón que exista y que puedas leer. Una casilla temporal de mail.tm sirve, y se maneja toda por API.

Qué hay que hacer

  1. Crear una casilla temporal en mail.tm máquina con internet
    bash
    # dominio disponible
DOM=$(curl -s https://api.mail.tm/domains | python3 -c 'import sys,json;print(json.load(sys.stdin)["hydra:member"][0]["domain"])')
ADDR="algo@$DOM"; PASS="Passw0rd!"
# crear cuenta
curl -s -X POST https://api.mail.tm/accounts -H 'Content-Type: application/json' \
  -d "{\"address\":\"$ADDR\",\"password\":\"$PASS\"}"
# token JWT de mail.tm (para leer el buzón)
TOK=$(curl -s -X POST https://api.mail.tm/token -H 'Content-Type: application/json' \
  -d "{\"address\":\"$ADDR\",\"password\":\"$PASS\"}" | python3 -c 'import sys,json;print(json.load(sys.stdin)["token"])')
echo $ADDR
  2. Pedirle al lab que mande el mail a esa dirección contenedor (reemplazá $ADDR por la dirección del paso anterior)
    bash
    $ curl -X POST "http://192.168.123.200/maketoken?email=$ADDR" -H "Tiki: Taka"
  3. Leer el buzón máquina con internet: listar mensajes, tomar el id y abrir el mensaje
    bash
    curl -s https://api.mail.tm/messages -H "Authorization: Bearer $TOK"
curl -s https://api.mail.tm/messages/<ID> -H "Authorization: Bearer $TOK"
  4. Mirar el HTML del mail, no solo el texto: trae pistas en blanco sobre blanco que se usan al final (ver abajo).
  5. Responder con el token contenedor
    bash
    $ curl -i -X POST http://192.168.123.200/papopepoparapapapapiparapopepo/response \
  -H "Tiki: Taka" -H "Content-Type: application/json" \
  -d '{"rta": "cGFjbz1wYWNvO3J0YT1zdHJpbmdfZXF1YWxz"}'
TokencGFjbz1wYWNvO3J0YT1zdHJpbmdfZXF1YWxz

Que es base64 de paco=paco;rta=string_equals (sirve para P5):

bash
$ echo 'cGFjbz1wYWNvO3J0YT1zdHJpbmdfZXF1YWxz' | base64 -d
paco=paco;rta=string_equals

Pistas ocultas del mail

Se ven seleccionando el texto o mirando el source: la clave SSH del vault está en un servidor HTTP del vault, en un puerto entre 49000 y 50000.

Si el mail no llega, el endpoint ofrecía /maketoken/damearchivoplis?email=....

P5

Validación de token sin estado

Tokens/dalequevamooo
Pregunta: si el servidor no tiene estado (no recuerda qué tokens emitió), ¿cómo sabe que el token no fue inventado? La respuesta está en el token mismo.

Qué hay que hacer

  1. Decodificar el token de P4 (base64) y leer el campo rta: paco=paco;rta=string_equals
  2. Responder contenedor
    bash
    $ curl -i -X POST http://192.168.123.200/dalequevamooo/response \
  -H "Tiki: Taka" -H "Content-Type: application/json" \
  -d '{"rta": "string_equals"}'
Respuestastring_equals

Concepto

Un servidor stateless valida un token sin guardarlo porque el token viene firmado (HMAC / firma): recalcula la firma sobre el payload con su clave secreta y la compara (comparación de strings, idealmente constant-time). Un token forjado no tendría firma válida. (El challenge además dejó la respuesta literal dentro del token como chiste.)

Guardala: string_equals es también la passphrase de la clave SSH del vault.

Objetivo final: The Vault

SSHHTTP192.168.0.238
Qué se pide:entrar por SSH al vault. Necesitás 4 datos: el puerto HTTP donde está la clave, el usuario, la clave privada y su passphrase.

Tras P5, el vault pasó a estar en la misma IP del SSH del lab (192.168.0.238), en otros puertos.

Qué hay que hacer

  1. Encontrar el servidor HTTP escaneando el rango de la pista del mail (49000–50000) tu máquina
    bash
    $ nmap -Pn -n --open -p49000-50000 192.168.0.238
49681/tcp open
  2. Abrir el listado de directorio y bajar el usuario y la clave tu máquina
    bash
    $ curl http://192.168.0.238:49681/                                  # listado
$ curl http://192.168.0.238:49681/IMPORTANTE_NOMBRE_DE_USUARIO.txt  # usuario: bububu
$ curl -s http://192.168.0.238:49681/supersecretkey -o ~/vaultkey
$ chmod 600 ~/vaultkey   # sin esto ssh rechaza la clave
  3. Conectarse al SSH del vault (puerto 12222). Cuando pida la passphrase: string_equals tu máquina
    bash
    $ ssh -o IPQoS=none -i ~/vaultkey -p 12222 bububu@192.168.0.238

Conceptos / detalles

python -m http.server (el Server: SimpleHTTP/... Python/... de la respuesta) arma un listado de directorio navegable → nunca dejes claves ahí.

La passphrase cifra la clave privada SSH en reposo (aes256-ctr + bcrypt en el header del archivo); SSH la pide al cargar la clave, es distinta del password de login.

El programa del vault es un TUI en Rust que paniqueaba con cannot sample empty range cuando la terminal tenía tamaño 0×0 (al pasarle un PTY sin winsize). Con una terminal real (o un PTY con TIOCSWINSZ seteado) renderiza bien.
